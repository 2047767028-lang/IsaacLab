## 一、起点扰动实验（v1，只扰第一个subtask的起点）

设计文档：`docs/接触锚定扰动增广_设计记录.md`。一句话：验证 DP 策略对"视觉伺服交接
给它那一瞬间"的初始位姿偏差的容忍边界，方法是在 MimicGen 生成时给自由空间段加位姿
扰动、接触段完全冻结。

**实验对象**：官方单臂 `Isaac-Stack-Cube-Franka-IK-Rel-Mimic-v0` + 官方10条源演示
(`datasets/annotated_dataset.hdf5`)。

**关键实现发现**：MimicGen 生成时第一个 subtask 的插值起点直接来自
`env.get_robot_eef_pose()`（钩子：`isaaclab_mimic/datagen/data_generator.py:538`
`merge_eef_subtask_trajectory`），而 reset 阶段已经有一个现成的机械臂关节高斯噪声事件
`randomize_franka_joint_state`（`stack_joint_pos_env_cfg.py` 的 `EventCfg`）——把它的
`std` 参数化即可让扰动天然流入生成链路，完全不用碰 MimicGen 核心代码。

**分支**：`perturbation-experiment`（从 v2.3.2 tag 切出，因为本机装的是 Isaac Lab
2.3.2，不能切去 `release/3.0.0-beta2`；仓库当时是分离头指针状态，切分支是为了让自动
提交有安全落点）。

**关键提交**：
- `467931872`：`FrankaCubeStackIKRelPerturbedMimicEnvCfg`（`PERTURB_STD`控制幅度）+
  新gym id `Isaac-Stack-Cube-Franka-IK-Rel-Mimic-Perturbed-v0` + sweep脚本。
- `6e5bd3404`：`PERTURB_SEED` 环境变量，配合复现性重跑。
- `8c8cd05a0`：`PERTURB_FIXED_ATTEMPTS`——修复"低成功率σ无限重试"隐患（见下面
  "已纠正的错误"）。
- `1303ff823`：sweep 脚本支持按seed分批、fsync写CSV、断点续跑。

**已纠正的错误（教训）**：曾经写过"`max_num_failures=25` 会兜底不拖慢"——这是错的，
只读了 `DataGenConfig.max_num_failures` 的文档字符串就当结论用，没验证执行代码。实测
σ=5.0 跑到337次尝试才凑够10个成功，才发现这个字段在 `generation.py` 的 `env_loop()`
里从未被读取（全代码库18个mimic env cfg都赋值但没一处真正判断）。真正的终止条件只有
"凑够`generation_num_trials`个成功"（默认`generation_guarantee=True`），低成功率σ会
无界重试。用 `PERTURB_FIXED_ATTEMPTS` 修复（切`generation_guarantee=False`，语义变成
"固定跑多少次尝试"）。**教训：配置字段文档字符串描述的是设计意图，不是实际生效行为，
必须读执行代码。**

**最终扫描配置**：20个σ值（0.00~8.00，弧度，逐关节高斯噪声幅度）× 5 seed × 每点固定
500次尝试 = 5万次生成尝试，实测约7小时。

**结果**（`docs/接触锚定扰动增广_实验记录_v1.md` + `docs/perturbation_sweep_v1_results/`，
commit `469bab130`）：σ=0.00~0.40 成功率持平36~37%（跨5seed差异<1pp）；σ=0.5~1.6
快速下降(32.8%→10.8%)；σ≥2.0变缓，σ=5.5/8.0趋稳1.6~1.8%。

**σ的物理含义澄清**：σ是7个手臂关节（不含夹爪）独立高斯噪声的标准差，单位弧度，不是
末端笛卡尔位移。实测末端执行器实际位移（200并行环境，reset后立刻读末端位姿，σ=0.0时
位置标准差仅4e-7米验证方法干净）：**σ=0.2→均值17.3cm；σ=0.4→均值35.1cm**。

**成功判据（用户定义，两层）**：第一层（生成阶段门槛）——加扰动后成功率跟原版
MimicGen差不多，只证明"没亏"；第二层（真正验证假设）——喂给LeRobot训DP/ACT+仿真
测评，看是否真的更好，v1曲线不能替代它。

## 二、全subtask扩展：两次失败尝试 + 弧线机制 v1→v2→v3

### 2.1 触发原因（结构性局限，不是bug）

`subtask_trajectory`（被插值的目标轨迹）只由物体位姿决定，跟起点扰动完全无关，插值
（`num_interpolation_steps=5`）一结束就完全接回原版MimicGen固定轨迹。不管扰1个还是
全部4个subtask，多样性只存在于每段开头约5帧，后面90%+帧跟不扰动时逐帧相同。

### 2.2 失败尝试①：物理瞬移（已废弃）

commit `5a813b3eb`+`5f219afa7`，已用 `git revert` 退回（`d9381bd46`+`a4ebcab7e`）。

踩出两个bug：①`get_robot_eef_pose()`读的是`obs_buf`观测缓存，靠`ee_frame`这个
`FrameTransformer`传感器供数，传感器只有被显式标记"过期"（`sensor.reset()`）才会
下次访问时重算，直接写关节状态不会触发。②更严重：`write_joint_state_to_sim`是纯
运动学瞬移，不经过物理步进，摩擦力约束没有时间传递，**手里抓着的方块不会跟着瞬移，
等于凭空脱手**——这是当时成功率暴跌到16%/0%的主因。

### 2.3 失败尝试②：弧线扰动 v1（离散控制点+直线插值，已废弃）

commit `0d2d676a2`，已revert（`420f7d890`）。

40次固定尝试成功率仅2.5%。用户追问"尾部明明收敛了为什么成功率还这么低"，逐帧算
"转向角"（相邻帧速度方向夹角）实测确认：位置数值确实收敛到0，但控制点之间是直线段，
每个控制点处（尤其弧线顶点）有真实的方向硬转折——frame 28测出116.9°瞬间转向（基线
同帧只有29.8°）。`sin(πu)`包络两端**数值**为0但**斜率**不为0，收敛边界还会叠加一次
速度台阶。

**关键澄清**：用户提出"调小幅度+调高密度"，讨论后确认这不是另一个方案，是同一个方案
的极限——密度推到极限（每帧都是控制点）就自动退化成"逐帧连续套函数"。但密度和幅度
不独立，不能自由二维网格扫描，所以直接把密度推到理论极限。

### 2.4 弧线扰动 v2（逐帧连续sin²包络，已实现并大规模验证）

commit `4ec4685e2`。不再有控制点/直线段，自由区间每帧直接算包络值。`sin²`比`sin`
多一层保证——两端**数值和斜率都是0**。删除了`PERTURB_ARC_NUM_POINTS`，只保留
`PERTURB_ARC_STD`（幅度,米,>0启用）和`PERTURB_ARC_FREEZE_FRAC`（冻结尾部比例,默认0.3）。

**v1 vs v2验证**（同seed同幅度std=0.05m）：v1成功率2.5%(1/40)→v2成功率10.0%(4/40)，
方向正确但n=40样本小，统计上约90%置信不到95%。10%量级本身提示：即便棱角问题解决，
4个subtask全部叠加几厘米级弧线扰动本身代价不小（粗算单subtask约55~60%成功率四次方
0.55^4≈9.2%，与10%量级吻合）。

**用户关键疑问：ACT会不会把不同轨迹"取均值"白费功夫？** 讨论结论（未实测，仅推理）：
大概率不会完全白费——每条扰动轨迹对应真实不同状态，动作从新轨迹本身重新导出（自洽，
不是同一状态硬贴不同标签），经典"平均导致穿墙"问题大概率不出现。真正风险集中在收敛区
（多条弧线收敛回同一尾部，若收敛得晚/急，state space会重叠）——方向一致+密度衰减这两条
约束本身就在压窄这个重叠区。ACT不是纯MSE回归是CVAE+L1，理论上能靠隐变量z区分模式但
部署时z通常不采样，大概率介于"纯回归被平均坏"和"DP能吃下多模态"之间——这正是设计文档
4.4节预判过的点，值得同时训DP和ACT对比，不是要回避的风险。最终还是要靠训练+测评回答。

**小规模探测**（11点,每点50次,freeze_frac=0.3）：0.5cm→34.0% / 1.0→40.0% / 1.2→34.0% /
1.5→30.0% / 2.0→28.0% / 3.0→14.0% / 5.0→10.0%。形状：0.5~1.2cm平台区；1.2cm后温和
下降；2.5cm往后陡降。

**正式大规模扫描**（用户拍板"优先精度"后定案）：15个幅度值（cm,密集段0.5~1.5步长0.1,
稀疏延伸1.8/2.0/2.5/3.0）× 5 seed × 每点500次固定尝试，实测耗时235~238秒/点（比模型
高约13%，弧线逐帧算包络比v1单纯reset噪声多算一点），总耗时约4.9小时。

**结果**（commit `1cb5b05e0`，`docs/perturbation_sweep_v2_arc_results/`）：
0.5cm→35.1% / 0.9→33.8% / 1.2→33.3% / 1.5→30.1% / 2.0→27.8% / 3.0→19.1%。0.5~0.9cm
缓降，1.0~1.2cm小幅波动（跨seed标准差1.6~1.8pp内，判断是噪声），1.5cm后降幅加大。
**3.0cm处仍在下降，没摸到"塌陷后企稳"的平台**——以后要往更大幅度补点这个网格还没覆盖。
派生数字（数学推算非实测）：假设4个subtask独立，单subtask隐含成功率≈合并成功率^(1/4)
≈74~77%。数据完整性已独立核对（8个随机点重开hdf5一致；combined.csv恰好75行无缺失）。

### 2.5 弧线扰动 v3（峰值位置可变，已实现，未跑规模验证）

**想法**（用户通过`/btw`命令提出，一个后台fork自动实现）：v2的`sin²(πu)`包络峰值固定
在自由区间正中央，但峰值出现在哪个位置是被浪费掉的自由度——可以偏早/偏晚不对称，
多产出一批路径形状不同的轨迹，是幅度、方向之外的第三个多样性维度。

**实现**（commit `1706bfffc`）：包络从固定对称的`sin²(πu)`泛化成`u^a·(1-u)^b`族
（阶数a+b=6），峰值位置`u*=a/(a+b)`由`PERTURB_ARC_PEAK_FRAC_MIN`/`_MAX`两个环境变量
控制范围，每次调用独立采样。内部把峰值位置钳制在(1/6, 5/6)保证a>1、b>1，维持v2的
"两端数值和导数都精确为0"硬约束。默认(0.5,0.5)锁定中心，向后兼容（但函数族已换，
跟v2不是逐字节相同曲线）。

**验证情况**：只做了纯数学验证（峰值位置精确命中、端点趋近0），**没跑Isaac Sim端到端
验证成功率影响**——超大规模仿真扫描该由协调者决定何时投入算力，不属于那次一次性实现
指令范围。**生产pi0.5训练数据时用的是v2默认行为（峰值锁中心），v3的峰值可变能力
目前完全没有被实际使用过。**

## 三、第二层验证启动：pi0.5训练数据交付（2026-08-22）

### 3.1 图像数据缺口（阻塞性，已解决）

之前所有σ/幅度扫描用纯状态任务（`...-Perturbed-v0`），生成的hdf5**没有任何图像观测**
——pi0.5是视觉-语言-动作模型，训不了。**解法**：仓库本来就有配套的、已注册的带摄像头
变体`Isaac-Stack-Cube-Franka-IK-Rel-Visuomotor-Mimic-v0`（`wrist_cam`+`table_cam`，
各200×200 RGB uint8），弧线扰动机制写在通用MimicGen生成代码里不绑定env cfg类，直接
换`--task`配合`PERTURB_ARC_STD`不用写新代码就能生成带图像数据。冒烟测试验证图像渲染
正常（人工看过截图，机械臂和方块清晰可见）。

### 3.2 仿真评测基础设施现状

场景资产有；`scripts/imitation_learning/robomimic/`下有评测脚本(`play.py`/
`robust_eval.py`)但**只认robomimic自己训练的policy checkpoint，不支持pi0.5**；仓库
搜不到任何openpi/pi0/policy_server代码，**没有现成的pi0.5仿真评测桥接**，需要仿照
genie_sim项目那套policy server模式自己搭，目前空白（暂不阻塞训练）；也没有robomimic→
LeRobot格式转换脚本，如果OpenPI需要LeRobot格式这步也要自己搭。

### 3.3 OpenPI/pi0.5数据量研究（查了官方仓库issue和AGENT_GUIDE.md，不是转述）

LeRobot官方维护者对"pi0.5微调简单PnP需要多少数据"的原话——"~50 episodes is a
reasonable start for a single-location PnP; go to 100-200 if you vary object/position."
（[issue #2378](https://github.com/huggingface/lerobot/issues/2378)）。我们的任务
属于"vary object/position"，官方建议100~200条。`AGENT_GUIDE.md` 7.3节训练配置表以
"~50条"为基准定pi0/pi05训练步数（batch 1~4，30k~80k步，显存受限需梯度累积）。
**结论：数据量不用追求越多越好，边际收益递减**，用户认可后定了300条/组的目标
（不再沿用832条那个量级）。

### 3.4 渲染并行度测试

渲染版本比纯状态生成慢约20倍（0.4s→9.7s/次尝试，num_envs=10，GPU渲染；CPU渲染更慢，
曾经CPU渲染3分钟才过场景加载就换成GPU）。**测过num_envs=24**，显存到11.3GB/12.3GB
（92%），前47次尝试更快（约7.7s/次）但**之后卡死6分多钟零进展**，同时GPU仍85%利用率、
CPU仍182%——吃资源但不推进，性质类似SIGPIPE卡死信号但这次没有subprocess.PIPE那层，
根因没查清楚。**已放弃更高并行度，正式生产统一用num_envs=10。**

### 3.5 执行中踩到的bug（已修复）

`Isaac-Stack-Cube-Franka-IK-Rel-Visuomotor-Mimic-v0`是独立于
`FrankaCubeStackIKRelPerturbedMimicEnvCfg`的另一个类，从没接过`PERTURB_STD`/
`PERTURB_FIXED_ATTEMPTS`——冒烟测试复现了"无界重试"（`--generation_num_trials 20`跑到
30+还不停），且"基线"组本该是`PERTURB_STD=0`纯净对照，实际会静默带着0.02关节噪声。
只有`PERTURB_ARC_STD`/`PERTURB_ARC_FREEZE_FRAC`是通用代码里读的没受影响（符合最初
设计预期）。**修法**：新建`FrankaCubeStackIKRelVisuomotorPerturbedMimicEnvCfg`+新
gym id`Isaac-Stack-Cube-Franka-IK-Rel-Visuomotor-Mimic-Perturbed-v0`（未改动任何已有
注册），commit `02ed4b14e`。踩出bug那次冒烟测试输出直接删了没用，重新验证修复生效
（精确停在目标次数）才继续。修复后渲染吞吐7.7秒/次尝试，比预估9.7s快。

### 3.6 轨迹平滑度复查（用带图像的正式task重新测）

目标轨迹本身仍平滑（`sin²`包络两端数值和导数都是0，数学结论不变）。但用更严格的
"转角序列自身有没有孤立尖峰"指标重新查，发现实际执行/记录下来的轨迹存在几处局部转角
尖峰（例如某帧测出99°，明显高于左右邻居帧）——判断更可能是**执行层面**的（1.2cm偏移
塞进约40~50帧短subtask段，differential IK控制器跟踪较"绕"的路径未必能完全平滑跟随），
不是v1那种设计层面硬棱角复发。参照点：baseline demo自身自然转角也能到156.8°，arc测出
最大值99.0°没有超过这个自然幅度，只是局部方向变化频率更高。记录供解读训练结果时参考，
没有因此叫停生产任务。
